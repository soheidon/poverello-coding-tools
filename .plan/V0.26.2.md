# Poverello Coding Tools v0.26.2 — Codex Autocodeの役割整理

- **計画状態:** §18、§21、§22、§23は、本書の各scopeに記録するCodex同一セッション内計画レビューと、ユーザーの明示指示に基づき`APPROVED FOR IMPLEMENTATION`。これは外部独立レビュー承認ではない。元の§1–§11および独立レビュー未完了の他scopeは、その履歴状態を保持する。
- **実装状態:** §18→§21→§22→§19–§21の整合・自動検証の順でAntigravityへ引き渡せる。未検証のDeepSeek実行は`UNAVAILABLE`のままとし、それ以外の実装可能作業は継続する。
- **レビュー後の原因調査:** §11.3。レビューdispatcher、CLI、PowerShellの結果を分けて記録。

## 1. 目的

Codex Autocodeの作業担当と独立レビュー担当の役割を分ける。ユーザーが指定した画面では「Codex CLI」ではなく「Codex」と表示し、Codex自身が計画・実装・修正・検証を行う作業主体であることを示す。

Codexの作業主体表示を、別プロセスの`codex exec`による自己レビューと混同させない。独立レビューが必要な場合はCodex以外の外部Reviewerが担当する。Codex本体が実行する作業は、Codex向けWorkflow Skillsとユーザーが明示的に開始したCodexタスクの契約に従う。

## 2. 現行仕様との関係

- v0.26.0計画§11ではCodexネイティブWorkflow Skillsを追加し、Codex自身をworkflow driverとして位置付けている。
- 同計画§12では、`pov-review-settings.json`のReviewer候補に`codex`を含め、`codex exec`を独立Reviewerとして起動する設計を追加している。
- この二つの役割がCodex Autocode上で混同されているため、v0.26.2ではCodex自身の作業実行と、別主体による独立レビューを明示的に分離する。
- v0.26.2はv0.26.0の既存実装や計画履歴を削除・巻き戻さず、変更範囲を本書の承認対象に限定する。

## 3. 用語と責務

### 3.1 Codex（作業主体）

ユーザーがCodexに依頼し、Codexが既存の`pov-plan-only`、`pov-build-review`、`pov-full-cycle`等のSkill契約に従って計画、実装、テスト、レビュー対応、報告を行う主体。Codex自身の同一セッション内レビューは「独立レビュー」と表示・計上しない。

### 3.2 Codex CLI（管理対象の実行ファイル）

`codex`実行ファイルおよびCLI Toolsで管理するインストール対象。Codex Autocode画面上の作業主体名には「Codex」を用い、「Codex CLI」という表示を出さない。CLI Toolsでは実行ファイルを区別する必要があるため、既存の正式な製品名「Codex CLI」を維持してよい。CLIを独立Reviewerとして起動することは本計画で認めない。

### 3.3 外部Reviewer

作業主体とは異なるCLI／プロセスで計画または実装を確認するReviewer。v0.26.2ではCodex CLIを含めず、DeepSeek Harnessおよび設定・実行条件が整う場合のGemini CLIを対象候補とする。実際に起動できるReviewerだけを選択結果に反映し、未導入・利用不能・安全な読み取り専用実行を保証できないものは`UNAVAILABLE`として扱う。失敗や未実行を承認とみなさない。

## 4. 変更方針

1. Codex Autocodeを「Codexが作業し、必要に応じて別主体が独立レビューする画面」として再定義する。
2. 添付画面では「Codex」を作業主体として表示し、独立Reviewerの選択肢・優先Reviewerから分ける。Codex Autocode上で作業主体を表す表示名は「Codex」とし、Codex CLIを自己レビューのために別プロセス起動しない。
3. UI名称の変更だけでCodex自身の実行連携が成立したと見なさない。既存のCodex Workflow Skills／CodexセッションからCodexが作業する経路を確認し、Poverelloから別の`codex exec`を自己レビュー用に起動しない。
4. Codex自身の計画・実装・修正・検証は、現在のCodexセッションでユーザーが依頼した作業とCodex Workflow Skillsに委ねる。Poverelloから現在のCodexセッションを隠れて起動・制御する新しいControllerは作らない。
5. 独立レビューを有効にする場合は、Codexとは別のReviewerだけを使う。外部Reviewer未選択の場合、Codex自身の自己レビューを独立承認として代用せず、独立レビュー状態を`SKIPPED`または`NOT CONFIGURED`と明示する。
6. 既存の`pov-review-settings.json`に保存された`reviewers.codex`と`priority_reviewer: "codex"`を調査する。Codexを作業主体へ移す際、旧値を外部Reviewerとして有効化し続けない。既存DeepSeek/Geminiの選択値は保持し、外部Reviewerが0件になった場合は未設定として明示して、暗黙に別CLIを有効化しない。
7. 旧Codex priorityは外部Reviewerの優先指定として引き継がない。選択済み外部Reviewerが1件なら、その唯一のReviewerを優先に設定可能だが、複数または0件の場合はユーザーに選択を求める。暗黙のfallbackはしない。
8. Gemini CLIの既存オプション、Windowsで安全な読み取り専用実行を確認できない場合の`UNAVAILABLE`、DeepSeek Harnessの既存実行安全条件、送信前同意、結果統合、timeout、プロセス回収契約を維持する。
9. Antigravity Autocodeの挙動と設定は変更しない。

## 5. UI・操作契約

- 「Codex」は作業主体として表示し、Reviewer選択・優先Reviewer欄から分離する。外部Reviewerの選択肢・優先Reviewer候補にはCodex CLIを出さない。
- Reviewer選択ボタンと優先Reviewerボタンは、現在のようにカード幅いっぱいへ均等に拡張しない。ラベルと操作状態が読める必要幅にし、内容に応じたコンパクトな横並びにする。
- CodexとDeepSeek Harnessの状態行と「優先 Reviewer」ブロックの間にある縦余白を縮小する。Codex CLIのインストール状態やversionを現在のCodex作業セッションの状態として誤表示しない。Codex側に正確なセッション状態を取得する方法がなければ、Codexのversion/status表示は省く。状態行の下余白・区切り線の上下余白は必要最小限にし、読みやすさは保つ。
- 「優先 Reviewer」ブロックでは、優先Reviewerの選択ボタン群をコンパクトにし、「設定を保存」ボタンを同じ行の右端へ配置する。ボタン同士や説明と重ならず、通常のウィンドウ幅で1行に収める。
- 画面幅が狭く同じ行に安全に収まらない場合のみ折り返し、保存ボタンを選択肢群の次の行の右端へ配置する。横スクロールやボタンの切り詰めを発生させない。
- Review Settings内に「CLIツール設定で管理」など、Settings → CLI Toolsへ移動するリンク・ボタンを表示しない。CLIの管理は既存のSettings画面から行う。
- 「Review Settings」見出しの右側にも丸囲みの`i`情報アイコンを置く。直下に常時表示している「Codex ワークフロースキルの複数CLI並列レビューを設定します（CODEX_HOME/pov-review-settings.json に保存）。」という説明文は常時表示せず、アイコンのクリック／タップで開くポップアップへ移す。
- この説明用アイコンもキーボードでフォーカス・起動でき、適切なaccessible nameと説明先の関連付けを持つ。全8言語、狭い画面、ライト/ダークテーマに対応する。
- この表示変更はCodex Autocode内の名称・役割を表す。CLI Toolsにおけるインストール対象の正式名や内部catalog IDを変更する場合は、別途互換性を確認する。
- Codexが実際の作業主体となる既存経路を維持・明示し、Codex CLI別プロセスによる自己レビューと混同させない。
- 外部ReviewerはCodexとは別主体として表示し、その結果のみを独立レビュー結果として扱う。
- 「優先 Reviewer」の見出し右側に、丸囲みの`i`情報アイコンを置く。判定説明は常時表示せず、アイコンをクリック／タップしたときに説明を表示する。再操作またはフォーカス移動で閉じられること。
- 情報アイコンはキーボードでフォーカス・起動でき、適切なaccessible nameと説明先の関連付けを持つ。全8言語（ja、en、de、es、fr、ko、zh-CN、zh-TW）に翻訳し、狭い画面・ライト/ダークテーマでも操作と視認性を保つ。
- 説明文は判定契約を平易に示す。文案: 「Reviewerの判定が分かれ、未解決のBlocking指摘がない場合は、優先Reviewerの判定を採用します。未解決のBlocking指摘がある場合は、優先Reviewerの判定だけで承認しません。」優先Reviewerの選択・保存・判定ロジックは変更しない。
- 「作業を依頼する」などCodex本体の現在セッションをPoverelloから自動起動するように誤解させる操作を設けない。実行開始はユーザーがCodexに依頼する既存経路に従う。
- 外部Reviewerが未設定の場合、独立レビューを実施したかのような`APPROVED`表示をしない。
- CLI ToolsでCodex CLIの導入・更新・状態を管理する場合も、それがCodex Autocodeの独立レビュー実行を意味しないことを区別する。

### 5.1 Reviewer別モデル・エフォート設定

- Codex Autocodeのモデル・エフォート設定は、実際に外部ReviewerとしてdispatchされるCLIにのみ提供する。
- DeepSeek Harness、および設定・安全条件が整った場合のGemini CLIには、Antigravity Autocodeと同じコンパクトなモデル・エフォートUIを提供する。
- Codex自身の作業モデル・エフォートは現在のCodexセッションが管理する。Poverelloにそのセッションを制御する既存APIが確認できない限り、PoverelloからCodexモデルを選ぶUIは作らず、Codex CLI用の値をCodex自身の設定であるかのように表示しない。
- Codexのモデル・エフォートをPoverello側から変更できるとする要件は、実装前にCodex公式の対応APIと既存連携を確認する。対応手段がなければ、その設定を架空の保存値として実装せず、この機能は`UNVERIFIED / BLOCKED`として止めて計画の再確認を行う。
- Antigravity Autocodeのコンパクトな見た目・操作部品・選択状態の表現を再利用する。Antigravity Autocodeの設定値・保存先・動作は変更しない。
- モデル候補とエフォート候補はCLIごとに定義し、現行の正式な引数・設定仕様で利用可能な値に限定する。
- 画面で選択した外部Reviewerのモデル・エフォートを実dispatchへ反映する。未知値、未対応値、適用不能な値はdispatch前に拒否し、黙って別モデルや既定値へ置換しない。
- 設定は外部Reviewerごとに保存・再読込し、既存設定との後方互換性と破損時fail-closedを維持する。

## 6. 実装前調査と停止条件

実装担当は、現行コード、設定schema、Codex Autocode UI、Workflow Skills、CLI dispatcher、および§12の受入テストを再確認し、次を確定する。

1. Codex本体の作業が、現行UIからどのように開始・管理されているか。
2. Codex Autocodeが現在`codex exec`をレビュー用途で起動するすべての経路。
3. Codex reviewer設定の永続化形式、旧設定の移行、UI表示、優先Reviewerの整合性。
4. 外部Reviewerが0件の場合のworkflow状態と、自己レビューを独立承認にしない既存境界。
5. Codex Workflow SkillsとCodex Autocodeの責務が二重化しない移行方法。
6. 現在のCodexセッションのモデル・エフォートを安全に読み取り・設定できる公式または既存の連携手段があるか。存在を確認できなければ、Codex用モデル・エフォートUIは実装しない。

Codex本体のセッションをPoverelloから直接起動・操作する必要があると判明した場合、または安全な設定移行・外部Reviewer分離を現行構造で実現できない場合は、実装範囲を拡張せず停止し、追加計画を提出する。

### 6.1 Codexレビュー設定の移行

現行既定設定には`reviewers.codex: true`および`priority_reviewer: "codex"`がある。移行ではこれらをCodex Autocodeの外部Reviewerとして引き続き有効にしてはならない。移行前に元設定の安全なバックアップを作成し、既存DeepSeek/Geminiの選択状態は保持する。旧Codexが優先Reviewerで、外部Reviewerが一つも選ばれていない場合は外部Reviewerなしの状態にし、未設定を明示する。複数の外部Reviewerが既に選択されていた場合は、優先Reviewerを自動決定せず再選択を求める。移行後のread-backとschema検証に失敗した場合は設定を上書きせず、復旧状態で停止する。

## 8. 受入条件

1. 添付画面でCodexが作業主体として「Codex」と表示され、外部Reviewer選択・優先Reviewer候補には表示されない。
2. Codex AutocodeでCodex自身が作業を担当し、Codex CLI別プロセスを自己レビューに起動しない。
3. Codex自身の作業や同一主体の自己確認を独立レビューとして計上しない。
4. Codex本体のセッションをPoverelloが非明示的に起動・操作しない。
5. 外部Reviewerが選択されていない場合、独立レビューを`SKIPPED` / `NOT CONFIGURED`として示し、`APPROVED`と扱わない。
6. `pov-review-settings.json`の既存Codex選択を外部Reviewerとして実効化せず、既存DeepSeek/Gemini設定は保持する。Codexが優先指定されていた場合に曖昧な自動選択を行わず、安全に移行または明示的な再設定要求を行う。
7. 優先Reviewerは実効Reviewer集合内に限られ、候補なし・選択不整合・未知schemaでfail-closedとなる。
8. 選択した外部Reviewerだけが起動し、失敗・timeout・unavailable・不完全結果は承認にならない。
9. Antigravity Autocode、無関係なCodex Workflow Skill機能、およびCLI Toolsの一般管理に回帰がない。3つのPoverello Codex Workflow Skill resourceは、Codex CLIを独立Reviewerとして起動しない契約へ更新される。
10. 対応するRust/Vitest/build/i18n検証を実施し、結果を計画書へ記録する。
11. 実CLIレビュー・モデル推論・認証変更・CLI導入/更新・ネットワーク操作・commit/push/tag/releaseは、別途明示許可がない限り行わない。
12. 「優先 Reviewer」右の情報アイコンがクリック／タップとキーボードで説明を開閉し、長文を常時表示せず、8言語・テーマ・狭い画面で正常に動作する。説明は既存の判定契約と一致し、判定ロジックは変えない。
13. Review SettingsにCLI Tools設定画面へ移動するリンク・ボタンがなく、既存のReviewer設定操作に回帰がない。
14. 「Review Settings」直下の説明文を常時表示せず、見出し横の情報アイコンからクリック／タップまたはキーボードでポップアップ表示できる。設定保存先を含む説明内容が正しく、8言語・テーマ・狭い画面で表示が崩れない。
15. Reviewer選択肢・優先Reviewer選択肢が内容に応じたコンパクトな幅で表示される。通常幅では優先Reviewer選択肢と「設定を保存」が同じ行に収まり、狭い幅では自然に折り返して全操作が可能である。
16. CLI状態行と「優先 Reviewer」ブロックの間隔が現状より明確に小さく、過大な空白がない。区切りと読みやすさを損なわず、8言語・テーマ・画面幅でレイアウトが崩れない。
17. Codex Autocodeに外部Reviewer別（DeepSeek Harness、有効時Gemini CLI）のモデル・エフォート設定があり、Antigravity Autocodeと同系統のコンパクトなUIで操作できる。Reviewer別に保存・再読込され、選択値が実dispatchへ反映される。Codex自身のモデル・エフォートは外部CLI設定として偽装しない。
18. モデル/effortの許可候補はReviewerごとの公式仕様に対応し、未知値・未対応値・CLIで適用不能な値はdispatch前に拒否する。設定値を黙って代替しない。
19. 旧設定schemaからの移行はバックアップ、atomic write、read-back検証を行い、旧Codex reviewer/priorityが外部dispatchされない。既存のDeepSeek/Gemini選択は維持され、選択不整合や未知schemaではfail-closedとなる。
20. 3つのPoverello Codex Workflow Skill resourceとそのdispatcherからCodex CLIの独立レビュー起動を除去する。古いinstalled Skillは無断上書きせず、UpdateAvailable/ProtectedConflict等の実状態を正しく示す。設定schemaが未対応のSkillはCodex CLIをfallback起動せず、エラーで停止する。

## 9. レビューと承認ゲート

- 本書の状態は`INCOMPLETE`。独立計画レビューを1回実行したがCodex CLIが判定を返さずexit 1となった。これは`APPROVED`でも`REQUEST_CHANGES`でもない。

- 実装着手には成功した独立計画レビューによる明示的な承認が必要。本レビューの許可は13ファイルへの1回に限られ、追加レビューや再試行の許可を含まない。
- Antigravity向け指示案は原因調査・修正候補を記録したもので、現時点では承認済み実装指示ではない。
- 計画承認後も実装承認範囲・禁止操作を越えない。実装完了後は別の独立実装レビューを行う。

### 15.1 目的

Codexによる計画作成・計画レビューとAntigravityによる実装の間で、Workflow Skillを通じた各計画・レビュー・実装報告がどの計画版およびどの指示に対応するかを追跡できるようにする。古い計画を基準にした作業、同じ指示への重複対応、計画改訂後の古い承認の誤適用を検出し、Skillの手順上で停止できるようにする。

### 15.2 正本と識別子

- 正本は既存の`.plan/V0.26.2.md`一つとする。改訂番号付きの複製ファイルや別の指示書を作らない。

- **Revision ID:** `R01`, `R02`, ...。履歴のない既存計画では過去の改訂を推定せず、追跡開始時点をこの作業範囲の`R01`とする。以後、規範的な計画本文・受入条件・実装範囲が変わるたびに単調増加させる。ログ追記、誤字修正、テスト結果追記だけでは増やさない。
- **Instruction ID:** `INS-001`, `INS-002`, ...。計画の内容・範囲を変えるユーザー指示ごとに一度だけ発行する。単なる質問、進捗確認、既存指示への回答は新規IDにしない。
- **Review ID:** `REV-001`, `REV-002`, ...。自己レビューと外部独立レビューを区別し、対象Revision IDと対象計画ハッシュを記録する。

### 15.3 計画ハッシュと改訂境界

- 各Revisionについて、Plan ID/Scope ID/Revision IDを含む規範ブロックのSHA-256を記録する。
- ブロック境界は`<!-- PLAN-SPEC:BEGIN plan_id=... scope_id=... revision=... -->`と`<!-- PLAN-SPEC:END -->`で囲む。ハッシュ対象はマーカー間の本文バイト列のみとし、開始マーカー属性、終了マーカー、Revision履歴、実行ログ、レビュー結果、可変ステータス、ハッシュ記録欄は含めない。
- 対象本文はUTF-8（BOMなし）/LFとし、ファイル先頭または本文にBOM、本文にCR-only改行があれば拒否する。CRLFだけをLFへ正規化し、空白、末尾改行、Unicode code pointはそれ以外変更しない。対象範囲はBEGIN行のLF直後からEND行の先頭バイト直前まで（間の空行を含む）。6つのSkillで同じ抽出・正規化手順を使い、共通fixtureと既知SHA-256で一致を検証する。
- Skillは引渡し前に正本から対象ブロックを一意に抽出し、Plan ID/Scope ID/Revision IDとSHA-256を再計算する。マーカーの重複・欠落、属性不一致、ハッシュ不一致ではfail-closedで停止する。
- ハッシュは対象仕様の同一性・stale検出用であり、作成者の真正性、履歴の改ざん不能性、承認そのものを暗号学的に証明するものではない。電子署名、Git commit、外部監査ログを実装したと主張しない。承認根拠には承認者・reviewer種別・判定・対象Hashを記録する。
- 規範的内容が変更された場合、過去Revisionを上書きして承認状態を引き継がない。新Revisionを発行し、以前の承認は旧Revisionに限定する。新Revisionは必要なレビューを再度通過するまで`REVIEW_REQUIRED`とする。

### 19.2 Reviewer実行契約

1. `codex_plus_external`では、Codex同一セッション内レビューと設定で選択された外部Reviewerをすべて実施対象とし、1件の不承認を理由に他のReviewerを省略しない。実行順序は設定上のpriorityから独立させる。並列・直列の実装方式は既存Dispatcher契約を維持してよいが、順序による早期停止は行わない。
2. `external_only`では選択された外部Reviewerをすべて実施対象とする。`codex_self_only`ではCodexのみ、`none`では既存のskip契約を維持する。
3. Reviewerごとの有効な最終判定（`APPROVED`または`REQUEST_CHANGES`）が揃った場合にだけ判定一致/不一致を裁定する。`INCOMPLETE`、`UNAVAILABLE`、`ERROR`、timeout、未実行、truncated等は判定ではなく実行状態であり、他Reviewerの結果やpriorityで上書きしない。必要なReviewerが1件でも有効判定を返さなければ全体を`INCOMPLETE`とする。
4. 全有効判定が一致すればその判定を採用する。判定が不一致なら、実効Reviewer集合に含まれ、かつ有効判定を返した`priority_reviewer`の判定を裁定結果とする。priorityが実行不能・未選択・有効判定なしの場合に、別Reviewerへ自動fallbackせず`INCOMPLETE`とする。
5. 優先されなかったReviewerの判定、指摘、重大度、根拠は全て維持し、最終報告・ログから削除しない。priorityは少数意見を消す権限や指摘の非表示化ではない。
6. いずれかの有効レビューに、未解決のBlocking Finding、安全性違反、必須受入テスト失敗、または計画上の非免除条件がある場合、priorityが`APPROVED`でも最終結果は`APPROVED`にできない。未解決Blocking Findingがあれば`REQUEST_CHANGES`（実行・環境上の未完了が主因なら`INCOMPLETE`）とし、該当Findingと裁定を報告する。priorityで無視できる指摘は、具体的根拠により非Blockingと判断された指摘だけとする。
7. 2件を超えるReviewerでも同じ規則を適用する。多数決は使わず、全必要Reviewerの完了後、判定一致なら共通判定、不一致なら有効なpriorityの判定を採用する。ただし§19.2 #6は常に優先する。

6. 証拠で特定できないhashは`UNRESOLVED`/`UnknownOrModified`として保護し、歴史版へ登録しない。その場合も現行版・証拠のある歴史版の分類、diff/backup/transaction機構、未知版の安全表示、および合成fixtureで検証可能な部分は実装・検証を続ける。原因未特定を理由に§22全体や後続scopeを停止しない。

### 22.3 状態・更新契約

- **Current:** 実ファイル集合と全hashが現行manifestに完全一致。更新不要。
- **KnownHistorical:** 相対パス集合と全raw hashが一つの出所確認済み歴史manifestに完全一致し、追加・欠落・型違いがない。バックアップ検証後、明示的なUpdate操作で最新版へ更新可能。
- **UserModified:** 既知releaseのpath集合に一致するが、1つ以上のfile hashが異なる。自動更新しない。file単位diff previewと完全バックアップを示し、別途明示確認された場合のみ更新可能。
- **UnknownOrModified:** 一つ以上の未知entry、既知版と異なるpath集合、出所未確認、または混合版。自動更新しない。相対file名・分類理由を表示し、diff/backup/明示確認の対象を限定する。未知entryは削除せず、overwrite対象に含めない。
- **Blocked / RecoveryRequired:** symlink/reparse、読取不能、transaction journal、backup検証失敗等の既存fail-closed状態を維持し、通常更新を拒否する。
- status responseは全fileごとに相対path、分類（current / historical / changed / missing / unmanaged / blocked）、expected hash/actual hashを必要最小限返せること。absolute pathやfile本文を診断ログへ入れない。
- 更新前にGUIでSkill名、更新対象file、ユーザー変更fileの有無、保持されるunknown entry、backup場所を表示する。変更版の更新は「バックアップして更新」等の明示確認を必須とする。確認はそのSkillと対象hash集合に結び付け、状態変更後や再読み込み後に古い確認を使わない。
- explicit confirmationを受けても、Unknown entry、symlink/reparse、分類不明、backup失敗、hash再検証失敗を上書き・削除してはならない。未管理entryは保持し、更新後もそれが残る場合は状態を`ProtectedConflict`相当で示す。

### 22.4 バックアップ・transaction・3 Skill部分失敗

1. `KnownHistorical`更新では、current templateではなく**照合に成功したhistorical manifestの全ファイル**とmetadataをバックアップする。UserModifiedの明示更新では、Skill配下の全通常file（unknown entryを含む、ただしsymlink/reparseは拒否）を保存し、変更前hash一覧を検証する。
2. backup完了・read-back hash検証後にだけ更新を開始する。journalは旧manifest/version、正確な旧・新file集合、各path/hash、置換進捗、backup identity、transaction状態を持つ。
3. fileごとの置換失敗時は状態を`RecoveryRequired`にし、成功したファイルだけを新Versionと誤表示しない。復旧はtransaction journalに記録した旧file集合から行い、現在のtemplate manifestだけを使って旧版を復元しない。
4. 3 Skillは独立transactionとし、一括操作がある場合も各Skill結果を個別に表示する。1件失敗時に成功した他Skillを隠さない、未処理Skillを誤って更新済みにしない、失敗Skillを自動再試行しない。全3件成功したときだけ総合完了を表示する。
5. 更新後は全file集合・hashを再走査し、現行manifestとの完全一致をread-back確認する。journalの削除/完了記録は確認後に行う。復旧不能・結果不明ではファイルを保全して停止する。

### 22.5 受入条件

1. 現行版fixtureは`Current`となりupdate不可/不要である。
2. 各公式historical release fixtureはpath setと全hashが一致した場合だけ`KnownHistorical`/`UpdateAvailable`となり、明示Updateで最新版へ更新できる。旧版hashを1つ変えたfixture、1つ欠落したfixture、未知file追加fixtureは自動更新されない。
