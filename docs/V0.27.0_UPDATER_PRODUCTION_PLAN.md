# Poverello Coding Tools v0.27.0 Updater 本番運用計画

- **計画状態:** 提案（本書は運用計画のみ。実装・鍵生成・ビルド・公開の許可ではない）
- **対象リポジトリ:** `soheidon/poverello-coding-tools`
- **対象バージョン:** v0.27.0（Updater付きの初回手動インストール版）
- **作成日:** 2026-11-08（JST）
- **前提:** 既存のTauri v2 Updaterを使用し、新しい更新機構は設計しない。

## 1. 推奨方針と現状結論

推奨する初回運用は、**管理者が選んだWindows PC上で、ユーザー管理鍵を使ってstable版NSISをローカル署名し、Codexが承認後の検証・GitHub操作を補助する方式**である。現在のWindows NSIS helperをそのまま使えるため、GitHub Actions workflowやGitHub Secretsを新設せずに済む。署名秘密鍵はCodexの入力やGitリポジトリに置かず、所有者が管理する暗号化保管先に置く。実際の鍵生成・設定・署名は本計画の範囲外である。

現行コードでは、Updater有効化に次の両方が必要である。

1. Windows stable channelのビルドに、Rust側のUpdater登録へ渡す公開鍵 `PCT_UPDATER_PUBLIC_KEY` が設定されていること。このプロジェクトではMinisign公開鍵テキスト全体をUTF-8/base64化した値を環境変数に渡す。
2. final patched NSIS artifactを署名する際に、対応する秘密鍵を `TAURI_SIGNING_PRIVATE_KEY` で使用できること。パスワード付き鍵なら `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` も必要。

公開鍵だけならクライアントの確認機能は有効になるが、署名済み更新ファイルは生成されない。秘密鍵だけでは信頼される公開鍵がアプリに組み込まれず、helperは拒否する。両方がない現在のstable buildは警告を出して成功し、Updater無効installerを作ることがある。この挙動を正式候補で見逃さないfail-closedガードを、実運用前に追加する。

v0.27.0はUpdater公開鍵を埋め込む初回版である。Updater非搭載の既存版からv0.27.0への自動更新はできず、最初のv0.27.0導入は手動installerを使う。v0.27.0自身はmanifestのversionが同じなら更新を提示しない。後続版（例: v0.27.1）が初の実Updater更新になる。Tauriは公開鍵でartifact署名を検証し、`requireSignedVersion`により署名に結び付いたversionとmanifest versionも照合する。[Tauri Updater公式資料](https://v2.tauri.app/plugin/updater/)

## 3. 本番配布アーキテクチャ

1. v0.27.0のstable Windows appへ本番公開鍵をcompile-timeで組み込み、Updater pluginを登録する。
2. Tauri v2 static manifest `latest.json`をGitHub Release assetとして配置する。
3. manifestの`windows-x86_64.url`は、同じtag内のversioned NSIS installerを指す。`signature`には対応`.sig`ファイルの**全文**を入れる。URLだけを書かない。
4. 各将来版は、同じ秘密鍵で、Poverello patch後の最終installer bytesを対象にアプリversion bound signatureを作る。
5. ユーザーが設定画面から手動確認または明示的installを選ぶ。署名確認後、NSIS passive installerが適用され、Windows pluginのinstall動作に従ってアプリが終了する。

GitHub endpointの`releases/latest`は最新の公開stable Releaseを基準にする。draftやprereleaseをProduction clientの試験配布場所として扱わない。試験にはテスト鍵とstaging endpointを組み込んだ別の試験buildを使う。

## 4. 署名鍵の生成・保管

### 4.1 方式比較

| 方式 | 既存構成への適合 | Secret管理 | 運用コスト | 評価 |
|---|---|---|---|---|
| 所有者管理Windows PCでローカル署名 | 既存`build-windows-nsis.ps1`を使用できる | 鍵ファイルとpasswordを所有者の管理下で保持。GitHubへ秘密鍵を預けない | 低い。ビルドPCの保全・バックアップが必要 | **推奨**。現状で最小の追加構成。 |
| GitHub Actions署名 | 現在workflowが確認されておらず、新規workflow・Windows runner・release jobが必要 | `TAURI_SIGNING_PRIVATE_KEY`とpasswordをGitHub Actions Secretsへ登録。公開鍵はsecretでなくrepository variableでもよい | 中〜高。workflow権限、runner、secret rotation、artifact provenanceを管理 | 将来、自動releaseを整備する場合に再評価。今回の最小運用には不要。 |

### 4.2 鍵生成と保管要件

鍵はアプリのUpdater用に一度生成し、以後の更新で同一の本番秘密鍵を継続使用する。Tauri CLIは`signer generate`で鍵ペアを作り、`--write-keys`でprivate key pathを指定できる。生成コマンドは対話terminalで実行し、空password/CI modeを使わず、passwordをコマンド引数やshell historyへ書かない。生成CLIの出力に秘密鍵値が含まれる可能性を想定し、出力をCodex chat・ログ・監査記録へ貼り付けない。[Tauri CLI signer資料](https://v2.tauri.app/reference/cli/)

計画する保管ルール:

- private keyファイルはrepository外（例: `%USERPROFILE%\.tauri\poverello\updater.key`）に置き、NTFS ACLを所有者だけに制限する。
- passwordは鍵ファイルと別のpassword managerに保管する。
- 暗号化されたオフラインbackupを2つ作り、異なる物理保管場所へ分ける。backupを復元できることを、秘密情報を外部へ開示しない方法で所有者が定期確認する。
- 公開鍵`.pub`は秘密ではない。git commit前に、実装方式に沿うbase64値として安定版binaryに含まれたことを確認する。private keyやpasswordはソース、`.env`、build log、GitHub Release assetへ入れない。
- 鍵紛失またはpassword紛失後は既存公開鍵を持つアプリ用の署名を作れない。新しい鍵へ切り替えるには新公開鍵を含む手動installerを再配布し、利用者に再導入してもらう計画が必要。漏えい時も同様に署名を止め、影響調査後に新鍵を含む手動版へ移行する。サーバー側の鍵差し替えだけでは既存appの信頼鍵は更新されない。

鍵生成の予定コマンド（**本計画では実行しない**）:

```powershell
Set-Location C:\Users\Sohei\dev\poverello-coding-tools\gui
npm run tauri -- signer generate --write-keys "$env:USERPROFILE\.tauri\poverello\updater.key"
```

事前に保存先を作成しACLを確認する。対話で十分な強度のpasswordを入力する。`--force`は使わない。生成後は`.pub`とprivate keyを取り違えず、公開鍵の指紋と対応関係を記録し、秘密値そのものは記録しない。Tauri v2 CLIの`--password`引数はコマンド行へ値を露出し得るため、この計画では対話promptを選ぶ。実際の生成時に使用するlock済みCLIのprompt挙動を事前確認する。

## 5. Stable buildと鍵なしbuildの防止

### 5.1 現行build helperの実動作

`npm run tauri:build:stable`はPowerShell helperを呼び、helperが`ANTHRO_BRIDGE_CHANNEL=stable`のTauri buildとpatched NSIS compileを行う。公開鍵envがあればkey formatを検証し、秘密鍵envがあれば`tauri.updater-artifacts.conf.json`を使う。最終Poverello patch済みinstallerを署名し、署名・version bindingをoffline verifyする。公開鍵・秘密鍵がなければ現在はwarningで続行しUpdater無効版を生成する。公開鍵だけのときもclientは有効化できるが、署名済みupdate artifactは作られない。

本番release候補に使う前に、helperへrelease専用の**必須署名モード**（例: `-RequireUpdaterSigning`）を追加する計画とする。そのmodeではfrontend/Rust/NSIS build前に、stable channel・Windows・両key env・public key encoding・private-key path/存在条件を確認し、欠落時はnonzero errorで停止する。加えて、lock済みCLI 2.12.4の実helpで`signer sign`は`TAURI_SIGNING_PRIVATE_KEY`を`--private-key`（key文字列）として、`TAURI_SIGNING_PRIVATE_KEY_PATH`を`--private-key-path`（file path）として解決することを確認した。現helperのfinal signing subprocessは`TAURI_SIGNING_PRIVATE_KEY`を継承したまま呼ぶため、build用にpathをこの変数へ設定するとfinal signerがpath文字列をkey文字列として読む可能性があり、署名失敗となる。このpath modeは本番未検証である。helperを最小修正し、build用key pathをfinal signerで`TAURI_SIGNING_PRIVATE_KEY_PATH`へ安全に引継ぎ、汎用`TAURI_SIGNING_PRIVATE_KEY`の競合値を一時除去・終了後復元/cleanupする。公開・秘密鍵値をargs/logへ出さない。対話型ephemeral fixture keyでpath経路とfinal artifact署名をテストする。通常Dev buildと明示的な非配布diagnostic buildは維持する。正式release手順では必須署名mode以外のbuildを受理しない。

### 5.2 公開鍵・署名鍵設定後の本番コマンド

下記はガード追加後に実行するコマンドの計画であり、現在のhelperに`-RequireUpdaterSigning`はまだ存在しない。

```powershell
Set-Location C:\Users\Sohei\dev\poverello-coding-tools\gui

$privatePath = Join-Path $env:USERPROFILE '.tauri\poverello\updater.key'
$publicPath  = Join-Path $env:USERPROFILE '.tauri\poverello\updater.key.pub'
$publicText  = [System.IO.File]::ReadAllText($publicPath)
$env:PCT_UPDATER_PUBLIC_KEY = [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes($publicText))
$env:TAURI_SIGNING_PRIVATE_KEY = $privatePath

# Passwordは承認済みpassword managerからmasked prompt経由でprocess envへ設定する。
# CLIへpassword引数として渡さず、標準出力・ transcript・shell historyへ出さない。
$securePassword = Read-Host 'Updater key password' -AsSecureString
$ptr = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($securePassword)
try {
  $env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($ptr)
  npm run tauri:build:stable -- -RequireUpdaterSigning
  if ($LASTEXITCODE -ne 0) { throw "Stable updater build failed: $LASTEXITCODE" }
}
finally {
  [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($ptr)
  Remove-Item Env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD -ErrorAction SilentlyContinue
  Remove-Item Env:TAURI_SIGNING_PRIVATE_KEY -ErrorAction SilentlyContinue
  Remove-Item Env:PCT_UPDATER_PUBLIC_KEY -ErrorAction SilentlyContinue
  $securePassword.Dispose()
}
```

保管方式に応じてprivate key/passwordの取得部分を調整する。秘密値はコマンドhistoryやログへ展開しない。Tauri公式資料ではprivate key path/contentとpasswordをprocess environmentから利用し、`.env`はbuild時の手段としてサポートしない。[Updater build資料](https://v2.tauri.app/plugin/updater/)

**現在の実装でguard追加前に手動ビルドする場合:** 同じenvを設定し、`npm run tauri:build:stable`を実行する。鍵が未設定のとき成功扱いにせず、helper logの`Updater client configured: True`と`Updater artifact signing enabled: True`を確認し、違えば成果物を全てrelease対象から外す。これは緊急の検査手順であり、将来のfail-closed guardの代替にはしない。

### 5.3 出力成果物

- `gui/src-tauri/target/release/bundle/nsis/Poverello-Coding-Tools_0.27.0_x64-setup.exe` — 8言語NSIS x64 installer。Tauri updater signatureと同じfinal bytes。
- 上記installerと同じdirectory/nameに`.exe.sig`を付けた署名ファイル。Tauri Minisign signatureに`--app-version 0.27.0`を結合。
- `latest.json` — NEWSのv0.27.0 section、versioned GitHub URL、`.sig`全文、installerの事前承認済SHA-256を用いて生成。
- 検証ログ、installer SHA-256/byte count、`.sig` SHA-256、manifest SHA-256、使用した公開鍵fingerprint、source commit/tag。ログにはprivate key/passwordを含めない。

Releaseへアップロードするinstallerは検証したファイルとbyte-for-byte同一とする。NSIS helperがsignature生成後にEXEを変えない順序を崩さない。Tauri build途中の古い`.sig`を使い回さない。

## 6. Staging実更新の検証経路

本番endpointは`releases/latest/download/latest.json`であり、v0.27.0候補を公開する前に同じendpointへv0.27.0より大きい更新を置くと、production Release/利用者へ公開される。このため本番秘密鍵を使った公開前のreal update/install smokeは行わない。

承認後の小規模な準備作業として、既存`build-windows-nsis.ps1`へ一時staging Tauri config overlayの受け渡しと、別出力先を扱う検証可能なoptionを追加する計画とする。overlayはendpointだけをテスト用のversioned GitHub prerelease `latest.json`へ向け、staging buildへは**一時テスト鍵**を組み込む。本番public/private keyは使わない。production clientのendpointは変更しない。実地検証は、test-keyで作ったstaging版を専用Windows test profile/VMに手動installし、より新しいtest versionをそのtest keyで署名してprereleaseへ置き、check/download/signature-verify/install/restartを実行する。ユーザー設定保持と失敗・中断時の挙動も記録する。test key/artifact/overlayは本番releaseへ混入させない。

試験prereleaseは公開GitHub assetになるため、作成・tag push・upload・削除にはそれぞれの明示authorizationを得る。public prerelease assetを避けたい場合は、所有者が選択したprivate HTTPS staging hostを別途準備する。現在のrepository/アプリにはprivate staging hostは確認されていないため、既存コードだけで公開前のエンドツーエンドUpdater install testが可能とはみなさない。

## 7. Signature・manifest・installerの検証

### 7.1 事前検証

1. branch/commit、`tauri.conf.json`、`Cargo.toml`、`package.json`、`NEWS.md`のversionが`0.27.0`である。
2. helper logでstable channel、公開鍵/署名が両方有効と確認でき、必須署名guardを通過した。
3. `ProductName=Poverello Coding Tools`、`ProductVersion=0.27.0`、x64 NSIS、8言語を確認する。
4. 最終installerのSHA-256を取得し、出力サイズ、ファイル名、ビルドログへ記録する。
5. final `.sig`を`gui/scripts/verify-updater-signature.mjs`で本番`.pub`に対しoffline検証する。正しい公開鍵、artifact bytes、trusted comment署名、signed version `0.27.0`の一致を確認する。改変installer・別versionでは拒否されることをfixture testで確認する。
6. manifest generatorへinstaller、`.sig`、review済SHA-256、NEWS、正確なURLを渡し、`latest.json`を生成する。
7. JSONを再読込し、`version=0.27.0`、`platforms.windows-x86_64.url`、同assetの`.sig`全文をbase64化した`signature`、NEWS notes、期待SHAを確認する。generatorは暗号verifyの代替ではないため、5を省略しない。
8. `npm run test:updater`、必要なfrontend/Rust regression、`git diff --check`を実施する。

本番公開鍵はbinaryに埋め込まれる信頼の根である。`.pub` fingerprintを計画時に公開鍵と照合し、後からenv値を取り替えて異なる鍵をbuildしていないことを記録する。公開鍵テキストを公開することはよいが、private key/passwordの有無をlog出力で確認することはしない。

### 7.2 GitHub Releaseとの照合

manifestに記載するasset URLは次の形で、tagとfile versionを一致させる。

```text
https://github.com/soheidon/poverello-coding-tools/releases/download/v0.27.0/Poverello-Coding-Tools_0.27.0_x64-setup.exe
```

公開assetは以下の3点に限定する。

1. `Poverello-Coding-Tools_0.27.0_x64-setup.exe`
2. `Poverello-Coding-Tools_0.27.0_x64-setup.exe.sig`
3. `latest.json`

Release notesは`NEWS.md`のv0.27.0節から取得する。GitHub Release tagは`v0.27.0`。Release assetをdraftへ用意した段階で名称・size・SHAを確認する。GitHub draftの資産URLはpublic updater smoke用として扱わず、draftから`.latest` manifestが提供されるとも想定しない。全pre-publication gate通過・最終承認後にReleaseを公開し、endpointのHTTP responseから取得したmanifest bytesが承認済`latest.json`と同一で、downloadしたinstallerのhash/signatureが一致することを確認する。

`gh release create ... --verify-tag --draft`は既存remote tagを要求し、assetを付けてdraftを作る例。公開は別段階の`gh release edit v0.27.0 --draft=false`で行う。現行GitHub CLIではasset付き`gh release create`はアップロード後に自動publishし得るので、draftフラグを必須とする。[GitHub CLI create](https://cli.github.com/manual/gh_release_create) [GitHub CLI edit](https://cli.github.com/manual/gh_release_edit)

予定コマンド（release authorizationとTag/Release存在の確認後のみ。**本計画では実行しない**）:

```powershell
gh release create v0.27.0 `
  'gui/src-tauri/target/release/bundle/nsis/Poverello-Coding-Tools_0.27.0_x64-setup.exe' `
  'gui/src-tauri/target/release/bundle/nsis/Poverello-Coding-Tools_0.27.0_x64-setup.exe.sig' `
  'gui/src-tauri/target/release/bundle/nsis/latest.json' `
  --repo soheidon/poverello-coding-tools `
  --verify-tag --draft `
  --title 'Poverello Coding Tools v0.27.0' `
  --notes-file '<temporary NEWS v0.27.0 notes file>'
```

draftとassetsを確認し、公開許可が別途得られた後にだけ:

```powershell
gh release edit v0.27.0 --repo soheidon/poverello-coding-tools --draft=false
```

remote mutation前には既存tag/releaseがないこと、target commit、tagger、branch/remote、asset一覧とhashを再確認する。同tag/releaseが存在していたり内容が異なれば止まり、overwriteしない。

## 8. GitHub Actionsを選ぶ場合

今回推奨しないが、将来CI化を選ぶ場合の必要物を列挙する。

- `TAURI_SIGNING_PRIVATE_KEY`: GitHub Actions Secret（秘密鍵のファイル本文またはCLIが読む所定のvalue）。
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`: GitHub Actions Secret。
- `PCT_UPDATER_PUBLIC_KEY`: repository variable（secretである必要はない）が適する。現実装のbase64 wire formatに合う値を保管する。
- `GITHUB_TOKEN`: repository Contents `write`を必要最小限に設定してdraft Release/assetsを作る。ActionsによるRelease作成にはContents writeが必要。Workflow fileを追加/変更するtokenには、token種別に応じWorkflow permissionも必要になり得る。[GitHub Actions permission](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) [Release API permissions](https://docs.github.com/en/rest/releases/releases)
- 固定・監査可能なWindows runner、lockfile準拠install、artifact hash、secret masking、job cleanup、draft-first、publish gateが必要。

この方式を採用しない場合、これらのGitHub Secrets/variablesを設定する必要はない。GitHub Actionsを後から追加する場合も、workflow追加・permission変更・secret登録は別の実装・管理承認で行う。

## 9. 失敗時の扱いと復旧

| 異常 | 計画する対応 |
|---|---|
| 公開鍵/private key envのどちらか欠落、format不正 | 必須署名modeでbuild前にfail。release assetを作らない。 |
| password不一致・署名失敗・version binding不一致 | build/verification失敗として停止。`.sig`/installer/manifestを差し替え、release候補再レビューを経る。 |
| manifestのversion/URL/arch/signature/NEWS/SHA不一致 | manifestを公開しない。固定version asset URLと`windows-x86_64`のみを再確認。 |
| download/network timeout | UIで更新失敗を報告。既存installed appを消さず、手動installer配布手順を残す。実機再試行は通信復旧後にする。 |
| 署名不正/改ざん/不正version | Updater拒否を期待条件とする。受理されたら即release停止、インストールしない。 |
| NSIS install/update途中失敗 | test VMで先に調べる。既存NSIS rollback/user data契約とlogを調査し、原因確定までは公開しない。 |
| key紛失/password紛失 | 既存鍵信頼アプリ向け署名を続けられない。新public key埋込版を手動再導入する計画へ切替。 |
| key漏えい疑い | 署名作成と公開を止め、影響期間・署名済assetを保存して調査。新key入り手動版移行の判断を行う。 |
| 公開後asset/manifest hash不一致 | 以降のRelease操作を止め、既存Releaseを上書きせず影響を評価する。別version修正Releaseの要否を判断する。 |

Tauri Updater署名はアップデートartifactの真正性を確認する署名である。Windows Authenticode署名はWindows publisher identity/OS trust UXを扱う別の証明書・署名方式であり、今回のTauri `.sig` gateを代替しない。Authenticodeを製品release gateに含めるかは別途明示決定する。

## 10. 役割分担

### A. Codexが実施可能な作業（個別承認後）

- 現行ファイル、lock済みTauri CLI/Updater仕様、version/endpoint/manifest整合をread-onlyで再確認する。
- 必須署名build guardとstaging config/output optionの最小実装、テスト、read-only review用証拠作成を行う（実装を別途承認された場合）。
- 所有者が管理するsecretを適切な方法で一時process envへ提供した後、秘密値を読んだり表示したりせずstable buildを実行できる。秘密環境値の設定・署名使用には別途明示承認が要る。
- `.sig` offline verification、hash、manifest生成、NSISの静的確認、draft release assetのhash照合を行う。
- 各git/remote/release操作が明示承認された場合、その承認範囲の操作と結果確認を行う。

### B. ユーザー判断・承認が必要

- 鍵運用方式、key custodian、暗号化・password・backup保管先を決める。
- 本番鍵の使用を承認し、build processへ安全に利用可能な状態にする。
- staging prereleaseを公開してよいか、test assetsがpublicになることを承認する。許可しないなら代替staging hostを決定する。
- 実機update testを行うtest version、Windows環境、データ保持の合否を決める。
- release candidate review後の各操作を個別に承認する：commit、branch push、tag作成/push、draft release/asset upload、Release publish、public endpointへの実update確認。

### C. 所有者が物理的に行う作業

- private key/passwordの独立backupを作り、保管先を管理する。Codexは所有者に代わって物理的に別場所へ保管・復元確認できない。
- staging prereleaseのpublic公開を許可しない場合、必要なprivate HTTPS staging環境を提供する。
- password manager/secure promptからcredentialをterminal processへ渡す場合は、所有者が画面上で入力する。秘密値をchat、issue、commit、release notesへ貼らない。

上記以外のGitHub Release作成・asset uploadは、適切な権限が接続され、明示承認があればCodexが実施できる。ユーザー手動UI操作を不要に要求しない。

## 11. 段階実行手順

1. **現状再確認:** 正本branch/commit、変更scope、CLI/plugin lock版、helper、config、version、public Release/tagの有無をread-only確認。
2. **運用決定:** Local Windows signingを第一候補として所有者が鍵保管・backup方式とstaging公開可否を決定する。Actionsは選択時のみSecrets/permission設計を追加。
3. **必要な最小実装を別途承認:** release-only `-RequireUpdaterSigning` guard、`signer sign`へのkey path安全引継ぎ、test config overlay/別出力の安全な受け渡しを追加し、ephemeral-key integration testとread-only reviewを通す。このタスクは本書作成の範囲外。
4. **鍵準備:** 所有者がTauri CLIで本番鍵を生成し、private key/passwordを保管・backup、public key fingerprintを確認する。Codexにsecretを送らない。
5. **stable build:** authorization後、process-scoped envを使い、必須署名modeでv0.27.0 Windows x64 NSISを生成する。8言語、helper log、output、signature、hashを確認。
6. **offline artifact検証:** final `.exe`/`.sig`/`latest.json`間のhash、version、signature、URL、NEWSを照合。test VMで初回手動installと設定保持を確認。
7. **staging updater検証:** test key/test endpointの専用buildとprereleaseで、test versionからより新しいtest versionへのcheck/download/signature/install/restartを行う。test assetsとtest keyがproduction候補から排除されたことを確認。
8. **release candidate全体review:** 選定したclean diffと全受入証拠をreviewする。Codexのself-reviewは独立reviewと表示しない。外部独立reviewが製品/組織要件で必要な場合はその方式を別に設定する。個人のReviewer設定値それ自体はアプリ機能のrelease条件ではない。
9. **最終承認:** ユーザーが署名済みcandidate hash、NEWS notes、3 assets、検証結果、残存riskを確認して公開可否を判断。
10. **Git操作:** commit、通常branch push、annotated `v0.27.0` tag作成/tag pushをそれぞれ個別承認の後に行い、identity/remote/commit/tagを再確認。
11. **Draft Release:** `NEWS.md` v0.27.0 notes、3 assetsでdraftを作成。asset名、size、SHA-256をupload後に確認。相違があればpublishしない。
12. **Publish:** draft/remote checksを確認し、明示承認後に公開。`releases/latest/download/latest.json`を取得し、公開bytesとlocal manifest、versioned asset、署名を比較する。
13. **Post-release smoke:** v0.27.0は初回導入版として手動installを確認。Updater動作の本番確認は次のversion（v0.27.1以降）を公開する時にProduction keyで署名したfuture updateを対象に行う。結果に問題があれば後続公開を止める。
